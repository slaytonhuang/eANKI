給 Claude Code 的交接文件。放在 `docs/SPEC.md`，並在專案根目錄的 `CLAUDE.md` 加一行：

```md

```

## 1. 專案概要

Android 單字學習 App。核心流程：**拍照取字 → 離線查字典 → 間隔重複複習**。

三個設計原則，衝突時以此排序：

1. **加入單字不打字、不等網路。** 掃描到寫入資料庫全程離線，無轉圈等待。
2. **每天的份量固定。** 掃描速度極快，若無節流，複習佇列會在隔天爆掉。
3. **複習節奏不能被打斷。** 20 張卡應在兩分鐘內刷完，中途不要有確認、動畫或載入。

## 3. 資料層：兩個獨立的資料庫

**不要把字典和使用者資料放在同一個 DB。** 字典很大但可拋棄式更新，使用者資料很小但必須能備份。

### A. 字典庫（唯讀，assets）

ECDICT + Tatoeba 預先建好的 SQLite，以 `Room.createFromAsset()` 或直接開 `SQLiteDatabase` 載入。App 永不寫入，版本升級時整包替換。

**決策（Phase 0 已實測定案）：砍成常用詞的精簡版內建在 assets，不做首次啟動下載。**

在 Galaxy Z Fold 5 上實測：

| 項目 | 實測值 |
|---|---|
| 字典檔解壓後 | 11.60 MB（49,500 筆） |
| 首次從 assets 複製到私有目錄（一次性） | 83 ms |
| 每次啟動開啟資料庫 | 0 ms |
| 單筆查詢 | 64 us |
| 批次查 20 個字（掃一張照片的量） | 1 ms |

### 精簡版怎麼建（`tools/build_dict.py`）

來源是 skywind3000/ECDICT 的**預建 SQLite**（`ecdict-sqlite-28.zip`，
解壓後 851 MB / 3,402,564 筆）。不自己解析 300 MB 的 CSV，省去寫解析器的風險。

篩選規則：

1. **有考試標籤的詞無條件保留**：zk / gk / cet4 / cet6 / ky / toefl / ielts / gre
   （14,942 筆），不受詞頻或任何其他條件影響
2. **其餘的詞要有詞頻排名**：`bnc > 0` 或 `frq > 0`
3. **大寫開頭且沒有考試標籤的詞，排名門檻收緊到 5000**
4. 必須有中文釋義

結果 **49,500 筆**，落在「常用 5~10 萬詞」的範圍內。

> **`bnc` 與 `frq` 是「排名」，數字越小越常用，而沒有排名的詞是 `NULL`（255 萬筆）
> 或 `0`（80 萬筆），不是一個很大的數字。**
> 所以 `ORDER BY frq LIMIT 50000` 會把 NULL 和 0 排在最前面，撈出來全是生僻字，
> 真正的高頻字一個都進不來。必須先排除沒排名的再排序。
> 兩個排名合併時取 `MIN()` 而非平均：只要在 BNC 或 COCA 任一語料庫算常用就收。

**規則 3 的理由**：只靠規則 2 會混進 8,496 個沒有考試標籤的大寫專有名詞 ——
英國郡鎮（Cambridgeshire、Staffordshire）、人名（Trevor、Mozart）、
機構縮寫（CNRS、ANOVA），對背單字毫無價值卻佔掉體積。但不能無腦砍掉所有大寫字，
China / English / Monday / America 都是大寫 —— 實測發現**這些該留的大寫詞全都有考試標籤**，
規則 1 已經保住它們（153 筆）。門檻只作用在「大寫 + 無標籤」這個交集。
取 5000 而非 10000：10000 會留下 Miami、Manhattan、Philadelphia、Ralph 這類零價值詞條。
DNA / AIDS / TV / CD / PC / UK / USA / CEO / Mr / Mrs 等重要縮寫都已驗證不受影響。

### 釋義是繁體（建置時轉換，執行期零成本）

**ECDICT 的 `translation` 是簡體中文。** 用 OpenCC 的 `s2twp` 設定在建置時
一次轉完存進 db（49,500 筆中 44,579 筆有變動），簡體 → 台灣正體並套用台灣慣用詞彙
（`网络`→`網路`、`计算机`→`電腦`、`软件`→`軟體`）。

**App 執行期不做任何轉換**，查出來就是繁體。`DictionaryRepository` 為此一行都沒改。

APK 體積拆解顯示字典不是大頭：完整 debug APK 51 MB，但其中 39 MB 是四個 ABI 的
native lib，**只含 `arm64-v8a` 的 APK 是 22.3 MB**（實機只裝一個 ABI，上架用
App Bundle 由 Play 自動切分）。字典的 11.60 MB 約佔最終下載量十分之一，
ML Kit 的模型與 native lib 才是主要來源。

為了省這 12 MB 去換一次網路下載、下載失敗的處理、以及首次使用就違反
「不等網路」原則，不划算。**首次啟動下載這個選項已排除。**

實作注意：**SQLite 無法直接開 assets 裡的檔案**（在 APK 內是壓縮的，拿不到 fd），
必須先整包複製到 app 私有目錄一次，之後比對檔案大小決定是否跳過。
驗證程式見 `phase0/app/src/main/java/com/example/eanki/phase0/DictDemo.java`。

### B. 使用者庫（讀寫，Room）

```
word_entry
  id            PK
  headword
  phonetic
  translation
  pos
  source        SCAN / MANUAL / IMPORT
  image_uri     來源照片，可為 null
  created_at

review_state
  word_id       複合主鍵之一 (FK → word_entry)
  direction     複合主鍵之一：EN_TO_ZH / ZH_TO_EN
  due_date
  interval
  ease_factor
  repetitions
  lapses
  last_reviewed
  grade_1       最近第 1 次評分（最新）
  grade_2       最近第 2 次評分
  grade_3       最近第 3 次評分

example
  id, word_id, text_en, text_zh, is_custom

tag / word_tag  多對多
```

**`review_state` 的主鍵必須是 `(word_id, direction)` 複合鍵。** 同一個字在「英→中」和「中→英」兩個方向的難度差很多，共用一組 interval 會在切換方向時破壞排程。Phase 2 只需實作 `EN_TO_ZH`，但 schema 先留好，未來開雙向卡不必動資料庫。

最近三次評分用三個 tinyint 欄位滾動儲存即可，不需另開表。

## 6. 互動決策（已定案，不要自行更動）

### 6.1 掃描以字典即時校對

掃描當下就查離線字典。查得到的字直接顯示釋義；**查不到的字以磚紅外框標示**並跳出提示，等使用者確認或修正。這等於用字典當 OCR 的即時校對，使用者不必自己逐字檢查。

### 6.2 方向切換

預設「英→中」（認得）。右上角按鈕可切到「中→英」（用得出來）。切換鍵放在複習畫面而非設定頁——使用者可能這輪練認字、下輪練拼寫。

兩個方向的排程各自獨立（見第 3 節複合主鍵）。

### 6.3 四顆評分鍵是階梯造型

**不是四個一樣的方塊。** 四個屬性同時由左向右遞增，讓「左負右正」不靠顏色也讀得出來：

| | 忘了 | 有點難 | 記得 | 太簡單 |
|---|---|---|---|---|
| 高度 | 54 | 64 | 74 | 84 |
| `flex-grow` / 權重 | 1 | 1.1 | 1.22 | 1.35 |
| 圓角 | 9 | 13 | 18 | 24 |
| 填色 | 只有外框 | 微填底 | 實心 | 實心最亮 |
| 色 | `#C4613F` 框 | `#A8823C` 框 | `#6FB49D` 底 | `#7FBFA9` 底 |
| 下次間隔 | 10 分鐘 | 1 天 | 4 天 | 10 天 |

四顆**底部對齊**，上緣形成階梯線；文字一律貼底（`justify-content: flex-end` + `padding-bottom`），四顆基線齊平。

按鈕下方顯示預估間隔，讓評分從「主觀感覺」變成「我希望多久後再看到它」，判斷更快。

半開模式下整排放大（高度 66 / 80 / 94 / 108）。

### 6.4 每日份量固定

兩個獨立的上限，不可合併：

- **新字上限**（預設 10 / 天）：掃描進來的字進入佇列，每天只放行這麼多進入複習流程。
  **放行順序是隨機的**，不是加入順序 —— 匯入 CSV 時 `created_at` 照檔案列順序給，
  而單字表多半按字母排，照加入順序會讓連續好幾天都在背 a 開頭的字
- **複習上限**（預設 60 / 天）：當天總量天花板，超過的順延，最久沒複習的優先

沒有新字節流機制的話，使用者拍一頁課本進 30 個字，隔天佇列就崩了。

**「選哪些卡」與「用什麼順序出現」是兩回事。** 上面的優先順序決定哪些卡進得了今天的
佇列；選完之後整份佇列會<b>打散</b>，到期卡與新字混在一起。不打散的話要先連做
十幾張剛複習過的字才會碰到新字，使用者的原話是「不然我會一直複習一樣的單字」。
打散不改變選中的是哪些卡，所以「最久沒複習的優先」在砍超額時不受影響。

**不做「當天掃到的字當晚複習」。** 雖然記憶效果好，但會讓每日份量劇烈波動。

### 6.5 熟悉度取最近三次評分

**不要存「最後一次評分」**，一次手滑就變紅點。取最近三次評分的眾數，**平手時取較差的那個**（寧可高估生疏程度）。

### 6.6 加強複習走獨立佇列

「一次複習所有不熟的字」（忘了 + 有點難）的結果**絕對不可寫回 SM-2 的 `due_date`**。否則每練一次就把這些字的排程往前擠，間隔越練越短，最後每天都在複習同一批字。

加強複習只更新熟悉度等級（第 6.5 節的三格滾動紀錄），完全不動排程。UI 上要明寫「不影響原本的排程」。

預設提供「只挑 20」選項——99 張卡一次刷完不實際，中途放棄比沒開始更挫折。

### 6.7 其他

- 提醒需有「沒有待複習就不提醒」開關，否則連續空通知會讓使用者直接關掉通知權限
- 熱力圖用「過去七天」滾動而非日曆週，週一打開才不會只看到一格

## 7. 響應式與摺疊裝置

### 斷點（用斷點，不要判斷機型）

| 寬度 | 版面 |
|---|---|
| `< 600dp` | 手機版：底部四分頁 + 單欄 |
| `≥ 600dp` | 展開版：**左側導覽軌** + 清單／詳情雙欄 |

用資源限定詞：`res/layout/` 與 `res/layout-sw600dp/`，系統自動選擇。這樣 Fold、平板、桌面模式全部涵蓋。

### Galaxy Z Fold 5 參考值

> 以下為記憶中的規格，未經查證。dp 值取決於密度與使用者的「顯示大小」設定，**請以實機實測為準**。

| | 外螢幕 | 內螢幕 |
|---|---|---|
| 解析度 | 2316 × 904 | 2176 × 1812 |
| 比例 | 約 23.1 : 9 | 約 6 : 5 |
| 估算寬度 | 約 344 dp | 約 690 dp |

外螢幕比標準 360dp 更窄但更高：左右留白縮到 16dp、熱力圖格子縮到 34、字級降一級；省下的橫向空間避免「有點難」等三字按鈕擠爆，多出的縱向空間可多顯示一筆清單。

內螢幕接近正方形，直接拉寬手機版會變成文字橫跨 690dp、底部分頁散落。改為導覽軌（寬 82dp）+ 清單欄（272dp）+ 詳情欄（其餘）。

### 半開（tabletop）模式

摺疊軸水平橫過中間時：**上半螢幕放單字卡**（字級放大到 64sp）、**下半螢幕放釋義與評分鍵**。避開摺疊軸，且正好把「看」和「按」分到兩個平面，非常適合翻卡。

### 三個必做事項

1. `AndroidManifest.xml` 加 `android:resizeableActivity="true"`，**不要鎖 `screenOrientation`**。否則內螢幕會被信箱框住，兩側全黑。
2. **摺疊會重建 Activity。** 複習進度、目前第幾張卡、是否已翻面，全部放 `ViewModel`，不可放 Activity/Fragment 成員變數。這是最容易漏、使用者最有感的 bug。
3. 偵測摺疊狀態：
   ```gradle
   implementation "androidx.window:window:1.2.0"
   implementation "androidx.window:window-java:1.2.0"
   ```
   Java 用 `WindowInfoTrackerCallbackAdapter` 取 `FoldingFeature`，讀 `getState()`（`HALF_OPENED` / `FLAT`）與 `getBounds()`（摺疊軸位置與粗細）。

雙欄清單／詳情直接用 `SlidingPaneLayout` 1.2.0+：它本身會讀 `FoldingFeature`，窄螢幕自動變單欄可滑動、寬螢幕自動並排且避開摺疊軸，Java 友善。

## 8. 開發順序

### Phase 0：可行性驗證（先做，不要跳過）

空專案，三個互不相干的 demo，能跑就好，UI 難看沒關係：

1. ML Kit 辨識一張圖片，log 印出所有單字與座標
2. TextToSpeech 念出 "apple"
3. 載入 ECDICT，查一個字印出釋義

### Phase 1：單字本核心（尚無掃描）

Room schema、手動輸入 → 自動帶出音標與中文 → 列表 → 點擊發音 → 編輯刪除。做完就有一個能用的 App，只是要手動打字。

### Phase 2：複習系統

SM-2 演算法（純 Java 類別，**先寫單元測試再寫 UI**）、翻卡介面、每日佇列、新字放行與複習上限、WorkManager 提醒。到這裡 App 的價值才成立——背單字的核心是複習排程，不是輸入方式。

### Phase 3：OCR 掃描

CameraX 預覽、拍照、ML Kit 辨識、自訂 View 疊加方框、點擊選取、批次查字典後一次寫入。同時做相簿上傳（同一條辨識管線，只是輸入源不同）。

**排在第三的原因**：掃描是輸入管道，單字本和複習系統沒好之前，掃進來的字沒有地方去。而且 bounding box 疊加點選是整個專案 UI 最難的一塊（要把 ML Kit 影像座標換算到 View 座標，還要處理旋轉與縮放），適合在其他部分穩定後再攻。

**Phase 0 實測補充的兩件事：**

1. **辨識結果必須先清洗才能查字典。** ML Kit 回傳的 element 會把標點黏在單字上
   （`apple,` `dog.` `Vocabulary:`），而且會改動大小寫（原圖 `over the lazy dog.`
   辨識成 `Over the Lazy dog.`）。查字典前要：去標點 → 轉小寫 → 還原詞形。
   字典查詢用 `COLLATE NOCASE` 可擋大小寫，但標點必須自己處理。
2. **透明背景的圖會讓辨識結果變成 0 且不報錯。** 透明像素解碼後變黑，
   黑字在黑底上完全認不到。相簿上傳前要檢查 `bitmap.hasAlpha()`，
   有 alpha 就先用 `Canvas` 壓上白底。

篩選後涵蓋 9,905 個單字、12,028 句，字典檔 14.4 → 16.2 MB。

**已完成：熟悉度統計、熟悉度篩選、加強複習。** 實作時定案的幾件事：

1. **「尚未開始」不算進四級，也不進堆疊條。** 四級是由評分定義的，
   沒評過分的字塞進任何一級都是錯的。而且新字每天只放行 10 個（第 6.4 節），
   未複習的池子會維持好幾個月的絕對多數（實測 1,338 比 136），
   放進去會讓四段全部壓成看不見。堆疊條的分母是「已評分的字」。
2. **堆疊條四段之間留 2dp 間隔，不另做顏色變體。**
   「記得」`#6FB49D` 與「太簡單」`#7FBFA9` 在條子上交界處分不出來，
   但第 4 節的色票要全 App 一致 —— 為單一畫面做變體，下個用到四級顏色的地方就對不上。
   間隔是固定寬、從總寬先扣，四段比例在數學上不受影響（實測前後比例一致）。
   四級色票集中在 `ui/familiarity/LevelPalette`，任何畫面都不該自己挑色。
3. **加強複習不寫 `review_log`。** 那張表餵的是熱力圖，而熱力圖問的是
   「我有沒有維持每天的複習份量」——那是**核心的習慣養成指標**，
   不是「今天有沒有打開 App」。

   加強複習也填熱力圖的話，會製造「今天有複習」的假象：格子滿了，
   但實際排定的複習佇列可能一張都沒動。那正是熱力圖本來要防止的事，
   指標一旦可以用不相干的活動刷滿，就不再能拿來看節奏。

   這跟加強複習「獨立佇列、絕不動排程」是同一個哲學：
   加強複習站在每日份量系統之外，就不該回頭影響那個系統的任何產出，
   無論是 `due_date` 還是熱力圖。

   因此 `review_log` 不需要「來源」欄位，也不需要 v4 migration。
4. **篩選畫面切換級別時清空勾選。** 跨級別累積勾選會讓底部「已選 18 個」
   指向使用者當下看不到的字。要練多級就分兩趟。
5. **「只挑 20」先塞滿「忘了」再輪到「有點難」**，不做隨機抽樣 ——
   隨機看起來公平，但使用者會練 20 個字卻半數是已經算記得住的。
6. 複習與加強複習<b>共用同一排階梯評分鍵</b>（`view_grade_row.xml`），
   兩邊手感必須一致。差別只在加強複習把按鈕下方的預估間隔整排收掉：
   那裡評分不改排程，顯示「4 天」會是謊話。

**已完成：Tatoeba 例句索引、來源照片 chip。** 定案的幾件事：

26. **備援例句不寫進使用者的資料庫，顯示時才查。**
    `ExampleSentence` 原本的註解暗示要把 Tatoeba 的句子存進 `example` 表，
    改成不存 —— 那是字典的附屬資料，會隨字典整包更新而變，
    複製一份進使用者庫只會讓備份變大，而且換字典後留下對不上的舊句子。
    使用者自己的例句永遠優先，備援只補位。
    （跟第 3 點「加強複習不寫 review_log」同一個道理：
    系統能重新產生的資料不該固化進備份。）
27. **`word_form` 加 `is_headword` 旗標，兩種查法共用一張表。**
    原本 `build_forms.py` 刻意排除「本身也是詞條的變化形」
    （`abandoning`、`running`），因為查釋義時直接命中必須優先 ——
    `saw` 是鋸子不是 `see`。但例句的需求相反：`abandoning` 沒有自己的句子時
    用 `abandon` 的完全合理。所以：
    查釋義 `WHERE form=? AND is_headword=0`、查例句不加條件。
    另開一張表會跟 `word_form` 重疊九成，白白多 1.6 MB。
28. **例句的中文轉繁體與一次性資料修復共用 `tools/zh_convert.py`。**
    同樣是 s2tw 加同一份排除清單，兩條路徑的結果才會一致。
    另外加了一小份台灣用語對照（意大利→義大利、軟件→軟體…），
    刻意不收有歧義的（計算機在台灣是 calculator、質量在物理是 mass）。
29. **Tatoeba 是開放投稿的語料庫，要過濾成人內容。**
    抽樣時抽到了。整句含黑名單詞就跳過，單字本身還是查得到，
    只是不會配到那種例句。
30. **來源照片 chip 預設收著。** 複習時要先想起意思，照片是想不起來時的線索；
    一開始就攤開等於洩漏答案。攤開狀態放 ViewModel —— 摺疊會重建 Activity，
    看到一半自己收起來在摺疊機上會很常發生。
    只有檔案真的還在才顯示 chip：顯示一個點了沒反應的 chip 比不顯示糟。

**已完成：匯出 / 備份。** 定案的幾件事：

18. **備份格式是 JSON，不是 CSV。** 備份要能<b>原樣還原</b>，而單字底下有
    一對多的例句、多對多的標籤、每個方向一份的排程狀態。攤平成 CSV 就得
    自己發明分隔規則，而那正是還原時最容易出錯的地方。
    「可讀」沒有放棄：輸出有縮排，文字編輯器打開就看得懂。
19. **檔案裡保留 `word_entry.id`。** example、word_tag、review_state、review_log
    全都用 word_id 指回來，重新編號會讓它們指到別的字上，
    而那種錯誤在畫面上只會顯示成「例句串到隔壁的單字去了」。
20. **還原是整批取代，不是合併。** 「恢復成匯出當時的狀態」只有取代做得到；
    合併會留下備份之後才刪掉的字。無法復原，所以要先預覽再確認。
21. **解析先做完，才碰資料庫；清空與寫回在同一個交易裡。**
    先清空再發現檔案是壞的，使用者就同時失去原本的資料與備份的資料。
    有測試專門餵壞檔進去，確認現有資料完好。
22. **備份寫到 SAF 選的位置，不是 App 私有目錄。** 私有目錄在解除安裝或
    清除資料時會一起消失 —— 而那正是最需要備份的兩個時刻。
23. **檔案格式有 `format` 與 `version`。** 版本比 App 新就直接拒絕：
    硬讀會安靜地漏掉新欄位，使用者以為還原成功了，而原本的資料已經被覆蓋。
24. **「還沒評過分」與「評了 0（忘了）」在檔案裡必須分得開。**
    grades 寫成 JSON null 而不是 0，否則還原後熟悉度會整批變成「忘了」。
25. **來源照片以 Base64 放進備份**（單檔上限 2 MB）。少了它，還原後那些單字
    會指向不存在的檔案，而使用者要到點開來源照片時才會發現備份其實不完整。
    圖檔在交易外寫 —— 檔案系統沒有交易，而且圖缺了資料本身仍然完整。

**已完成：設定頁。** 定案的幾件事：

11. **設定存 SharedPreferences，不開 Room 表。** 少數幾個純量、沒有查詢也沒有關聯，
    開一張表只會多一次 migration 的機會。
12. **讀出來的值一律夾限**（`DailyLimits.clamped`）。SharedPreferences 會被備份還原
    或舊版本寫進超出範圍的值，直接信任它等於讓每日份量被任意數字接管。
    新字上限可以是 0（「先把手上的消化完」），<b>但複習上限的下限是 5 不是 0</b>——
    0 會讓佇列永遠是空的，看起來像壞掉，而且等於靜靜關掉第三原則。
13. **沒有「儲存」鍵，每一項即時生效。** 八個選項而已，多一個儲存步驟只會製造
    「改了但忘了存」。改動後要主動同步的只有兩處：提醒相關要立刻重排 WorkManager
    （不然要等明天 Worker 跑完才套用），語速要立刻推給 TTS 引擎。
    <b>每日上限不需要</b>——佇列在 session 開始時讀一次就定案，
    中途改設定不會動到正在進行的佇列（第三原則）。
14. **Slider 的值要先對齊 stepSize。** `Slider.setValue` 對「不是 valueFrom + n×step」
    的數字會直接丟例外，夾限擋得住範圍、擋不住步進。備份還原來的 63 或 0.85
    會讓使用者一進設定頁就當掉。
15. **設定頁不顯示相機鍵。** 它浮在內容上，在設定頁會剛好蓋住某一列的開關，
    使用者看不到那個設定目前是開是關。設定頁是全 App 唯一「不會想在這裡加字」
    的畫面，而且相機鍵只差一個分頁，第一原則沒有被犧牲。
16. **電池最佳化與通知權限兩列只帶去系統設定、不代為要求。**
    `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 需要的權限，Google Play
    對用途審查很嚴，單字 App 不在允許的類別裡。兩列都把<b>目前狀態</b>顯示出來
    （「會被延後」「已開啟」），因為兩者出問題時的症狀都是「提醒沒來」，
    使用者只會以為功能壞了。
17. **沒有「下載字典更新」。** 第 3 節已定案內建精簡版、不做下載，
    字典跟著 App 版本走。設定頁提供的是「重建字典檔」，給本機那份被截斷
    或損壞時修復用。

**已完成：單字本的搜尋與標籤篩選。** 定案的幾件事：

7. **過濾在 SQL 做，不是撈全部再用 Java 篩。** 第 9 節記著這份清單之後要換

8. **關鍵字要跳脫 `%` 與 `_`。** 兩者在 `LIKE` 裡是萬用字元，不處理的話

9. **排序把「完全相同」與「開頭相符」拉到前面。** 搜 account 時

- ~~字典檔精簡策略（內建精簡版 vs 首次啟動下載）——Phase 0 決定~~
  **已定案：內建精簡版（實際 49,500 筆，釋義已轉繁體），不做下載。**
  加上詞形還原索引（`word_form`，43,215 筆）之後，實機上的字典檔是 14.4 MB。
  篩選規則與實測數據見第 3 節 A。
- **單字本列表之後要換成 Paging 3。** `WordDao.observeAll()` 目前是
  `SELECT * FROM word_entry`，一次把全部載進記憶體。
  **觸發門檻約一萬筆**：到那個量級開始會有感（載入延遲、`DiffUtil` 每次比對全部項目、
  所有釋義字串常駐記憶體、GC 壓力），兩三萬筆會明顯。
  **現在不改的理由**：實測 1,464 筆時 Java Heap 只有 14.6 MB、捲動掉幀率 0.39%、
  Missed Vsync 0，離痛點還很遠；而 Paging 會讓 DAO、Adapter、ViewModel 都變複雜。
  等之後匯入更多單字表、資料量真的上去了再回頭處理。
- ~~匯入資料的部首碼位問題~~ **已修復。** 記錄在這裡是因為坑本身會再來。

  **症狀**：匯入的 1,464 筆裡有 594 筆釋義、1,114 筆例句，中文字用的是
  康熙部首（U+2F00–U+2FD5）或 CJK 部首補充（U+2E80–U+2EF3）的碼位，
  不是一般漢字。「濫用」的「用」是 U+2F64 而不是 U+7528。
  外觀一模一樣，但中文搜尋對那些字完全失效 ——
  實測搜「用」回傳 0 筆，實際有 36 筆存的是部首碼位，
  而使用者用任何輸入法都打不出那個碼位。

  **成因**：從 PDF 抽取文字時的字型編碼陷阱，字型把字對應到外觀相同的部首碼位。

  **這個坑有第二層**：使用者的轉檔流程本來就會跑 s2twp 轉繁體，
  但 OpenCC 看到的是部首碼位而不是簡體字，所以那些字<b>逃過了繁簡轉換</b>。
  部首還原之後才會有 157 筆殘留簡體字現形（儿几厂广无气网虫隶）。
  修的順序只能是「先還原碼位，再轉繁」，反過來沒有用。

  **修法（v3 → v4 migration + 一次性離線補轉）**：
  1. 碼位還原在 `data/text/HanRadicalNormalizer`，migration `MIGRATION_3_4` 套用。
     康熙部首交給 NFKC；CJK 部首補充沒有相容分解，用對照表。
     <b>只逐字處理落在部首區段的字元，不對整串做 NFKC</b> ——
     那會把全形括號換成半形，釋義的樣子就變了。
  2. 康熙部首<b>不做繁簡判斷</b>。陷阱是用長得一樣的字換原字，
     所以 `⼏` 的原字就是「几」不是「幾」，`⾥` 是「里」不是「裡」。
     對它們跑 s2twp 反而會弄錯。
  3. 殘留簡體字用 OpenCC `s2tw` 離線補轉。
     <b>不能用 s2twp</b>（會做詞彙替換：文件→檔案、支持→支援、高清→高畫質），
     也<b>不能用 s2t</b>（會轉成港式異體：里→裏、群→羣、吃→喫、床→牀）。
     s2tw 另有四處過度轉換要排除：了→瞭（語助詞）、岩→巖、准→準（獲准）、
     以及人名「馬里奧」「謝里」的里→裡。

  **防止再發生**：`ImportRow` 解析每個欄位時都會還原碼位，
  並回報兩件事到匯入摘要 —— 對照表沒涵蓋的部首字元、以及殘留的簡體字。
  簡體只回報不自動轉（`data/text/SimplifiedDetector`）：
  繁簡是看上下文的（里／裡、干／乾／幹），轉錯會改掉釋義的意思，
  比留著原字糟。偵測字表由 OpenCC 產生、再用已轉繁的字典釋義當語料濾過，
  否則 s2t 會把 里/干/斗 也列進去，警告一直亮就沒人看。

- **App 名稱未定。** 自用工具，不影響任何功能。
- 「太簡單」在階梯造型下是視覺最大最亮的一顆，可能誘導誤按（代價是 10 天不再看到該字）。若實測發現誤按率高，改為讓「記得」維持最亮、「太簡單」僅尺寸最大但顏色收斂
- 「忘了」是最小的一顆（54dp），但它是使用者最挫折時按的鍵。若實測難按，整排平移為 60/68/76/84
- **翻卡與換卡的轉場幾乎每次掉一幀**（實測 69 幀中 13 幀 janky，99th 17ms，
  120Hz 的預算是 8.3ms）。推測瓶頸是大字級襯線字體在翻面時改字級觸發的重新排版。
  <b>跟資料量無關</b>——複習畫面一次只渲染一張卡。
  觸發條件：覺得翻卡手感不夠俐落時，從 `ReviewActivity.renderFace()`
  與 `activity_review.xml` 的卡片層級查起。
- **例句備援涵蓋 9,905 個單字（字典 49,500 筆的 20%）。**
  Tatoeba 的中英對照語料只有 78k 組配對，常用字幾乎都有、罕用字大多沒有——
  而例句最需要的正是常用字。觸發條件：如果發現常掃到的字沒有例句，
  調 `tools/build_examples.py` 的 `MAX_DIFFICULTY` 或 `MAX_PER_WORD` 重建。
